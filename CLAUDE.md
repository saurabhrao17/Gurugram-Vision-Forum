# Gurugram Vision Forum website

Read HANDOFF.md first; it holds the context, research, design rules and roadmap.

## Stack (decided 7 Oct 2026, see docs/decisions.md and docs/deploy.md)
- Vercel hosts the static site from `site/` and the API functions in `api/`. Supabase holds the data (Postgres, Storage, Auth). No Cloudflare, no Freshdesk.
- Domain: gurugramvisionforum.org, bought on Vercel 8 Oct 2026 and attached to the project; gurgaonvisionforum.com (the Gurgaon spelling, .com) and both www hosts redirect to it with 308. `SITE_URL` in Vercel is the public origin.

## Layout
- `site/` is the website: `index.html`, `styles.css`, `data.js`, `app.js`, plus `boot.js`. Static, hash-routed, no framework, no build step unless we deliberately add one.
- `api/index.js` is the single Vercel function, reached through the `/api/:path*` rewrite in `vercel.json`: a router that maps every `/api/*` path to a handler in `lib/handlers/` (`report`, `report/upload-url`, `report/attach`, `status`, `join`, `dashboard`, `ward`, `geocode`, `content`, `news`, `health`, `visitor`, `pulse`, `subscribe`, `triage/joins`, `triage/subscribers`, `triage/newsletter`, `triage/reports/:ref/ask`, `triage/reports/:ref/extract`, `triage/social`, `sitemap`, `indexnow`, `gsc`, `page/*`, `cron/daily`, `hooks/whatsapp`, `hooks/exotel`, `hooks/email`, `triage/*`). Add a route by adding a handler and one line in the router. The Hobby plan allows 12 functions per deployment, so never add files under `api/`. `lib/` holds shared code. ESM, Node 20+.
- The volunteer desk is the `#/desk` route inside `site/app.js` (English only; internal tool). It talks only to `/api/triage/*` with a Supabase Auth bearer token. `triage.html` is a redirect kept for old links. Desk design (owner's ask, 8 Oct 2026, modelled on help-desk and mail products: Zendesk, Front, Intercom, Linear, Gmail): a sidebar shell (`.desk`, `.dside`, `.dnav` groups Work / Team / Publish / Audience / Watch, the same `.tab` buttons and ids as before) with a `.dhead` title block per tab; the Reports tab is a workspace whose stage pipeline (`.pipeline`, counts from the list summary) is the stage filter, whose rows (`.rrow`) carry stage colour, tags, age and the next step, and whose ticket drawer (`.sheet.wide`) opens with a stage stepper, a **Next step** card (`nextStep()` in app.js: map → collect → file → follow up / escalate → resolve, with a button that jumps to the right field) and section cards; the Inbox is a two-pane mail client (`.mail`: `.mlist` rows with avatar, sender, subject, snippet, time, unread state; `.mread` reading pane with status, notes, files and the linked ticket; on phones the pane replaces the list with a Back button). The Content tab is a publishing workspace: counts strip, Posts / Settings sub-views (`[data-ctab]` switches `.cpane`), a composer card (`#composer`, opened by New post or Edit, sections Basics / Draft with AI / Write (English and Hindi side by side) / Media and links / Publish) and a post list with thumbnails, tags, search and kind chips; Settings holds the social links and the round-up. The Newsletter tab is a two-pane composer (campaign list on the left, the editor on the right). Team (`roles` tab, panel `tRoles`) is the people roster (name, mobile, desk role, active, wards read-only, Remove) with an Add-a-person composer; **Ward assignments** (`assign` tab, panel `tAssign`; owner and coordinator) has a By ward view (36 rows, a select per role; a change PUTs the old holder without the ward and the new holder with it, through `PUT /api/triage/team`) and a By person view (`#assignBody`: staged chips, the "1-6, 9, 12" Add control and Save per person). `SHOTS=<dir> node tests/smoke.mjs` saves screenshots of the desk screens for a visual check.
- Maps: MapLibre with OpenStreetMap tiles, lazy-loaded from unpkg only when a map is shown; `/api/geocode` and `/api/ward` do search and ward detection server-side (Google when `GOOGLE_MAPS_KEY` is set). Ward polygons live in `ward_boundaries` (PostGIS), sector names in `area_wards`.
- `supabase/migrations/` is the schema; `supabase/seed.sql` is generated from `site/data.js` by `npm run seed`. Apply both to a new project in that order.
- `archive/` holds the single-file v3 build (what was published as the Claude artifact) and the older v2. Reference only; do not edit.
- `data/` holds the content exports (JSON and CSVs) that seed the master-data sheet. `site/data.js` is the source of truth until the sheet exists; regenerate the exports from it, not the other way round.
- `design/tokens-and-components.css` is a copy of `site/styles.css` kept as the design-system reference; update both together.
- `docs/` holds the launch guide and the civic-platform benchmark. `deck/` holds the original PDF.
- `tests/smoke.mjs` is the Playwright smoke test (file:// pass plus an http pass with a mocked API); `tests/unit/` are node:test unit tests for the API validation. Run both before committing.

## Rules
- Content lives in `site/data.js` (`window.GVF`). Edit data, not markup, to change issues, portals, charters, roles, wards, Hindi strings.
- Every issue type carries what its official portal needs (`GVF.FILING`: fields and document slots with required flags). The report form collects these at step 3, the API stores them in `reports.extra` and `reports.attachments` (files go to the private `report-photos` bucket through one-hour upload tokens and signed URLs; the browser never holds a storage key), and the desk shows the checklist with what is missing. When a portal changes its form, update `FILING`, run `npm run seed`, and write the live `issue_types.filing` with `gvf_set_filing()`.
- Design tokens and components are in `styles.css`; keep the navy-led palette, saffron as accent only (never saffron text on white), Anek/Noto type, 44 px targets, visible focus, reduced-motion support.
- No public contact details (owner's decision, 8 Oct 2026): the site shows no email address, phone number or person's name anywhere, including the footer, About, privacy, accessibility, the gate consent, the SEO pages' footer and Organization data, and the round-up disclosure. The Report and Join forms are the only channels; offline fallbacks offer "Send again" and copy, never an email. Data-subject requests go through the Join form's note.
- Public copy is non-partisan; never add party framing to civic tools. Party appears only as a factual field (ward table).
- Never display or transmit a reporter's phone number publicly; public pages and dashboards show counts, never names.
- Dashboard shows commitments vs actuals with a date and source; never present the deck's targets as results.
- Every external link must be an official page; update `GVF.VERIFIED` when links are checked.
- The site is fully bilingual. Static markup uses `data-i18n`, `data-i18n-ph` and `data-i18n-aria` keys with Hindi in `GVF.HI`. Everything rendered from data or from app.js goes through `hs("English text")`, which looks the English up in `GVF.HS` (English → Hindi); values sent to the API stay English (`unh()` maps a typed Hindi area back; selects keep English `value` attributes). Blog posts carry `hb` (Hindi HTML). When English copy changes, add or update the matching `HS` entry; the smoke test fails on any Latin word left in Hindi mode that is not an acronym.
- Secrets never go in the HTML or JS; they belong in the Vercel environment (`.env.example` lists them). The browser only ever calls `/api/*`. Security headers live in `vercel.json` (HSTS, a Content-Security-Policy that allows scripts only from the site and unpkg, X-Frame-Options, nosniff, Referrer-Policy) and the same CSP is a meta tag in `index.html` so the smoke test enforces it; when a new external origin is needed add it to both. Every table has RLS on and only the service role (the API) reads data; the desk gets its own data through `/api/triage/*` after `requireStaff`.
- Reports are confidential (owner's decision, 8 Oct 2026, non-negotiable): what a resident reports is seen only by the team on the desk. The public gets COUNTS only (per ward, per issue type, per stage: dashboard, `/ward/:n`, the Wards page, the weekly round-up), never a reference, place, date, description, photo or ticket of any one report. There is no public report page, map or feed; `/r/<ref>` and `/map` show a "Reports are private" notice for old links. The only per-report view outside the desk is the reporter's own track view (`/api/status`: reference plus the last four digits of their mobile; stage and dates only). Never add a public endpoint that returns report rows.
- Notifications go through the `outbox` table (filled by the `reports_notify_stage` trigger and the daily cron) and are sent by `/api/cron/daily`; never email from a request handler. Inbound WhatsApp and Exotel webhooks create reports with their `source` and dedupe on `inbound_messages`.
- Visitor registration: `GVF.GATE` in `site/data.js` decides when the gate appears (after `after` ms or `pages` views, never on the desk; both 0 switches it off) and how hard it is: `mode: "soft"` (default; name and mobile required, email, sector, PIN optional, a "Not now" that waits `snooze_days`) or `mode: "hard"` (must be completed). Registrations go to `visitors` through `/api/visitor`; the same endpoint logs first-party events (page_view, report_start, report_submit, gate_shown, gate_done…) in `visitor_events`; no third-party tracker. A submitted report registers the reporter with the same details. On the report form name, mobile, email and PIN code are required (owner's decision; the gate stays soft). Keep the gate notice (`g.*` keys) in step with `docs/visitor-data-research.md` (DPDP Act obligations) and bump `GATE.version` when the wording changes.
- Roles (`lib/auth.js`, enforced in every `/api/triage/*` handler with `requireStaff(req, roles)`): `owner` sees everything; `coordinator` runs operations (all reports and wards, team, join requests, content, pulse, health; cannot see visitor data or create owners/coordinators); `triage` is a ward volunteer and gets only the reports and map of the wards allotted in `ward_volunteers`; `content` is the content team and gets only Content and Pulse. The desk hides tabs with `tabsFor(role)` in `app.js` but the API is the real gate; keep both lists in step and add a unit test in `tests/unit/roles.test.mjs` for any new endpoint.
- Translation: `POST /api/triage/translate` (owner, coordinator, content) turns title, summary and body from English into Hindi or back on the same free-first AI chain as drafting; the desk Content form auto-fills the other language when a field changes and the counterpart is empty, and never overwrites typed text without the Translate button. It answers 503 `translate_unavailable` without a key, and the desk says which free key to add.
- Gurugram pulse: the daily cron scans public discussion (Reddit r/gurgaon and r/gurugram public JSON and Google News RSS searches; never the Forum's own reports, which are confidential to the team) into `signals`, classified by `lib/signals.js` into the site's issue types with an area where one is named, and computes the week's `insights` (topics, areas, examples, trend, suggested actions such as a cleaning drive, camp or townhall; narrated by the free AI chain when a key is set, rule-based otherwise). `/pulse` and `GET /api/pulse` are public and carry counts, titles and public links only; the desk Pulse tab (`/api/triage/insights`) adds the raw signals. X/Twitter has no free API and Quora forbids scraping, so neither is read; never store a poster's name or handle.
- Team content: the desk Content tab (owner, coordinator, content) publishes stories, news, photos, videos, social posts, testimonials and pop-ups to `posts` (public read through `/api/content`, media in the public `media` bucket); the site renders them in Updates, as home pop-ups and footer social links, with the static `BLOG`/`MEDIA` as fallback. "Draft with AI" uses a free API key first (`GEMINI_API_KEY`, then `GROQ_API_KEY`) and `ANTHROPIC_API_KEY` only as a paid fallback; keep it that way, the Forum runs on donations. Official news (`/api/news`, page `/news`) is collected daily by the cron from `data/news-sources.json` into `news_items`; add sources there.
- Social publishing (owner's ask, 8 Oct 2026: maintain the social accounts from the desk through free APIs): `lib/social.js` posts a published post to the Forum's own accounts through each platform's official API, nothing in between: Facebook Page and Instagram (Meta Graph API, free; `META_PAGE_ID`, `META_PAGE_TOKEN`, `META_IG_USER_ID`; Instagram needs a photo), Telegram channel (Bot API, free; `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`), Bluesky (AT Protocol, free; `BLUESKY_HANDLE`, `BLUESKY_APP_PASSWORD`) and X (API v2 with OAuth 1.0a, pay-per-use credits; `X_API_KEY`, `X_API_SECRET`, `X_ACCESS_TOKEN`, `X_ACCESS_SECRET`). LinkedIn company pages and WhatsApp Channels have no self-serve API (see docs/social-publishing-research.md), so they stay manual. A platform is connected when all its variables are set; the desk (`GET /api/triage/social`) only learns which are connected. Every attempt is a row in `social_posts` (queued → sent | failed | skipped, unique per post and platform): the composer's "Also share to" boxes queue and send when a post is saved as published, a row's Share button does the same for a published post (`POST /api/triage/social {post_id, platforms}`, content roles), and the cron step `social` (analyse group) retries queued rows up to 3 attempts. Text is title, clipped summary, the post's public URL (`/blog/:slug` or `/updates`) and up to four hashtags from the tags, within each platform's limit; never a reporter's details, never the `hold` tag. Keys stay in Vercel; add a platform by adding a publisher in `lib/social.js`, its env names in `PLATFORMS`, and a test in `tests/unit/social.test.mjs`.
- Automated upkeep (owner's ask, 8 Oct 2026: links must never be stale): the API runs in Vercel's Mumbai region (`regions: ["bom1"]` in `vercel.json`) so India-only government hosts answer; the `fetch` cron (news, links, page audit, mentions) runs at 00:00 IST (18:30 UTC) and checks EVERY official link every night; the `analyse` cron (pulse, round-up, digest, audience, social, SLA digest, daily brief, outbox, retention) runs at 08:00 IST (02:30 UTC) so the morning brief and the day's mail go out together (`link_status`); `/api/dashboard` returns `links: { checked_at, total, broken }` and the site footer shows that live date ("Links verified …", or "checked …; N being fixed"), never a hard-coded one; `/api/health` and the desk Health tab show database, storage, cron, email queue, links and news freshness; GitHub Actions: `qa.yml` runs unit and smoke tests on every push and, nightly at 04:00 IST, `scripts/check-health.mjs` against production (fails on a down database, a stale cron, broken links or failed mail and opens the "Nightly checks failed" issue), and `uptime.yml` probes the home page, `/api/health` and a ward page every 30 minutes and opens or closes a "Site down" issue. The owner should add a free external monitor (UptimeRobot or Better Stack, 5-minute checks with SMS) for faster alerts.
- Real URLs (`/report`, `/track`, `/ward`…) are rewritten to `index.html` in `vercel.json` and moved into the hash at boot; keep the view list in `vercel.json` and in the boot regex in `app.js` in step.
- Automated SEO desk (owner's ask, 8 Oct 2026: the SEO work a retained consultant would do, run by the machine and shown on the desk): the desk's SEO tab (owner, coordinator, content; `GET /api/triage/seo`) reads what the cron produced and never computes on the page. `lib/seo/audit.js` holds it all: `pageList()` (the sitemap's URL set), `auditHtml()` (title 15-70, description 50-160, one H1, self canonical, hreflang trio, JSON-LD parses, Open Graph, lang, viewport, noindex, alt text, word count by kind, internal links; the app's routes share one shell and get the technical rules only) scored 0-100 into `seo_pages` by the cron step `seo` (40 least-recently-checked pages a night; duplicates across pages are computed on read), `vitalsStep` (PageSpeed Insights, mobile, one key page a night from `VITALS_PAGES`; needs the free `PAGESPEED_API_KEY`, since keyless calls share an anonymous quota that answers 429, and the tab says so) into `seo_vitals`, `mentionsStep` (Google News search for the Forum's name) into `seo_mentions`, `opportunities()` (fortnight's public signals by issue and area against recent posts; "Draft this" opens the composer) and `checklist()` (17 items, automatic ones proved by the rows; `seo.gsc_verified` and `seo.bing_verified` are the only manual ticks, saved through `PUT /api/triage/content`). The `seo` and `mentions` steps ride the midnight `fetch` cron (quick, no key); the cron group `seo` (all three) is called step by step by `.github/workflows/seo-cron.yml` at 03:00 IST with the repository secret `CRON_SECRET`, the only place `vitals` runs (the Hobby plan has two Vercel crons and PageSpeed takes most of a minute). Page `<title>`s stay short: `withBrand()` adds " | Gurugram Vision Forum" only while the whole title fits 70 characters; the H1 keeps the full question. Never let the audit read a report, and never add a page type without adding it to `pageList()`.
- GEO, content clusters and the deeper audit (owner's ask, 8 Oct 2026: "everything automated"): **GEO** (`lib/seo/geo.js`): `/llms.txt` and `/llms-full.txt` (handler `llms.js`, rewrites in `vercel.json`) are built on request from `site/data.js` and the published posts; `site/robots.txt` names the AI crawlers (`AI_BOTS`) in their own group and repeats the closed paths; `geoChecks()` in the audit scores each rendered page's readiness to be quoted (direct answer under the H1, FAQ/HowTo/Article data, a date, official sources, question headings, Organization, depth) into `facts.geo`; the cron step `geo` puts three of `geoQuestions()` a night to Gemini with Google Search grounding (`GEMINI_API_KEY`, `GEO_MODEL`) and stores whether the answer cited the site in `seo_geo`. Guide and ward pages carry `dateModified` and a visible "facts last checked" line from `GVF.VERIFIED`; ward pages open with a direct answer and cite MCG and the district's representatives page. **Clusters** (`lib/seo/clusters.js`): one per issue, the guide is the pillar; a post belongs by an issue id in its tags (a static `GVF.BLOG` entry names it in `k`) or by two or more classifier keywords, never on one weak hit; guides list their cluster's posts and every post links to its pillar guide and up to three siblings (`about` in its Article data); `clusterHealth()` marks gap / stale / thin / covered for the desk. **Audit**: schema completeness per type, internal links captured per page (`facts.out`), targets outside the sitemap checked 25 a night (`seo_links`), broken links and orphans computed on read (`linkGraph`, orphans only once the whole sitemap is crawled), site checks (`seo_site`: robots, sitemap, llms.txt, security headers, www and http redirects). **Search data**: `lib/seo/gsc.js` (service account JWT signed with node:crypto, `GSC_SERVICE_ACCOUNT`, `GSC_SITE`; 28-day queries and pages into `seo_search`, 10 URL inspections a night into `seo_index`, sitemap status) and `lib/seo/bing.js` (`BING_WEBMASTER_API_KEY`; the site found with GetUserSites; queries, pages, crawl stats). Steps `geo`, `gsc`, `bing` run only from `seo-cron.yml`. The desk's SEO tab has sub-tabs Overview (activity, write next, connections, the 30-row checklist, mentions), Pages, Clusters, GEO, Search data and Speed; `/api/triage/seo` returns `connections` as booleans only, never a key, and the site checks as `sitechecks` (`site` is the origin).
- Search pages: `/guides`, `/guide/:issue`, `/ward/:n`, `/blog`, `/blog/:slug` (and the same under `/hi/`) are server-rendered HTML from `lib/seo/*` through the `page/*` route (rewrites in `vercel.json`), built only from the site's data and live counts: unique per page, canonical + hreflang + JSON-LD, never a template with only a name swapped (Google's doorway rule). `/sitemap.xml`, `site/robots.txt`, `/indexnow-key.txt` (`INDEXNOW_KEY`) and the Search Console file route (`GSC_FILE`) complete it. `SITE_URL` is the public origin everywhere on the server. Bump `BUILD_DATE` in `lib/seo/site.js` when page templates change. Read `docs/growth-and-seo-research.md` before adding any generated page.
- Weekly round-up (`lib/autopost.js`, cron steps `autopost`, `digest`, `indexnow`): one post a week drafted from the pulse, the week's official notices, the Forum's counts (editorially, only once 50 reports exist) and the suggested actions; stored unpublished with `source = auto:weekly:<ISO week>`, byline "Gurugram Vision Forum data desk" and a disclosure line; publishes itself after `site_settings.autopost.review_hours` (48 by default; 0 at once, -1 never) unless tagged `hold` from the desk. It skips a week with nothing to say. Never raise the volume above one post a week or drop the disclosure: that is the line between people-first content and scaled content abuse.
- Team structure (owner's ask, 8 Oct 2026): a **coordinator** covers a cluster of 5-6 wards; each ward has a **main lead** and a **support lead** (`ward_volunteers.role` in coordinator | lead | support, one person per ward and role). Assignment is per person from the desk's Roles tab (`GET/PUT /api/triage/team`, `set_staff_wards()` replaces the person's list in one transaction); `staff` carries `phone` and `active`. `ward_assignments` shows who covers which ward. The staff account role `coordinator` (desk access) is distinct from the ward role.
- Desk inbox (owner's ask: nothing stays in a mailbox nobody reads): `POST /api/hooks/email` stores inbound mail in `inbox` (Resend `email.received` webhooks verified with `RESEND_WEBHOOK_SECRET` and fetched with `RESEND_API_KEY`, or any forwarder with `EMAIL_HOOK_TOKEN`); the desk's Inbox tab (owner, coordinator; `/api/triage/inbox`, PATCH `/api/triage/inbox/:id`) merges those mails with new join requests and unmapped reports into one stream with new/read/done and notes.
- Asking the reporter for missing items (owner's ask, 8 Oct 2026: from the desk, never a mail app, always by ticket ID): the ticket's "Ask the reporter for the missing items" button calls `POST /api/triage/reports/:ref/ask` (`lib/handlers/triage/ask.js`; report roles, ward scope), which mails the reporter from the Forum's address through the outbox at once (bilingual, kind `ask`, the reference in the subject as `[GVF-…]`, Reply-To `DESK_EMAIL` or `desk@<site host>`), logs a timeline event and sets `reports.asked_at`; with no email on the report it answers 409 with the text to copy for WhatsApp or SMS. Every inbound mail goes through `lib/replies.js` before it is stored: a reference in the subject or body links the row (`inbox.report_id`, `report_ref`), image and PDF attachments are stored in `report-photos` under `<ref>/reply-…` and attached to the report (the first open required photo slot first, then kind `reply`), and a "Reply from the reporter" event with actor `reporter` goes on the timeline. The ticket drawer shows the replies (`replies` in `GET /api/triage/reports/:ref`) with "Fill the missing fields from this reply", which calls `POST /api/triage/reports/:ref/extract {inbox_id}` (same free-first AI chain; 503 `extract_unavailable` without a key) and shows a proposal; only "Apply" writes, as a normal PATCH of `extra` with a note. Nothing is written to a ticket by the model on its own.
- Performance and the daily brief: `ward_ageing()` and `staff_activity()` feed `GET /api/triage/metrics` (owner, coordinator) and the desk's Performance tab (ageing buckets 0-3, 4-7, 8-21, 22+ days per ward, overdue, last week's flow, per-person actions and a "no activity in 7 days" flag). The cron step `brief` (analyse group, 08:00 IST) builds the brief with `lib/brief.js` and queues it to every active owner and coordinator by email (`outbox`, kind `brief`) and sends owners the one-line version on WhatsApp through the approved template `WHATSAPP_BRIEF_TEMPLATE` (default `gvf_daily_brief`, one body parameter) once the Meta values are set. Never put a reporter's details in the brief.
- Join requests (`POST /api/join` → table `joins`): the desk's Join requests tab (owner, coordinator; `/api/triage/joins`, PATCH `/api/triage/joins/:id`) works them through new → contacted → onboarded | declined with internal notes and a CSV export; each new request queues an outbox mail to `COORDINATOR_EMAIL` naming the person and role only (no phone or email in mail).
- Subscribers (`/api/subscribe`, table `subscribers`): double opt-in, email and language only, unsubscribe link in every digest; only confirmed, not-unsubscribed rows are ever mailed. The desk's Subscribers tab (owner only, like Visitors; `GET/POST /api/triage/subscribers`, `PATCH /api/triage/subscribers/:id` with `action` unsubscribe | resubscribe | sync | delete; CSV export) is where the sign-ups are seen; "add" from the desk only sends the confirmation mail, nobody is ever subscribed without clicking it. Newsletter tool (owner's ask, 8 Oct 2026: free or cheapest with rich features): the list is mirrored to **Resend contacts** through `lib/audience.js` (the mail provider the site already uses; free to 1,000 contacts with unlimited Broadcasts, a rich editor and its own unsubscribe link): a confirmation pushes the contact, a stop pushes `unsubscribed`, an erasure deletes it, and Resend's `contact.updated` / `contact.deleted` webhooks on `/api/hooks/email` stop the Forum's digest too; `synced_at` is cleared on every change and the cron step `audience` (analyse group) re-pushes anything with `synced_at` null. Needs a full-access `RESEND_API_KEY`; `RESEND_AUDIENCE_ID` only for older accounts on the audience-scoped paths; `AUDIENCE_SYNC=off` disables the mirror. Only the address and language are ever sent, never a name. Beyond 1,000 contacts the CSV export moves the list to Brevo (free, 300 mails a day) or Kit (free to 10,000); do not add a second list tool before that.
- Newsletter from the desk (owner's decision, 8 Oct 2026: the team operates on the desk, never in the mail provider's dashboard): the desk's Newsletter tab (owner, coordinator, content; `GET/POST /api/triage/newsletter`, `POST /api/triage/newsletter/preview`, `POST /api/triage/newsletter/:id {action: test|send}`, `DELETE /:id`; table `campaigns`) writes a campaign in English and Hindi as plain text (`lib/newsletter.js` turns it into escaped HTML: blank line = paragraph, `## ` heading, `- ` list, URLs linked; HTML in the body is refused), previews it, mails a test to the signed-in person, and sends it to every confirmed subscriber. Only owner and coordinator may send. The channel is chosen by the server, never by hand: with `RESEND_SEGMENT_ID` (or `RESEND_AUDIENCE_ID`) and the mirror on, one Resend Broadcast to the mirrored contacts (no daily cap, Resend's `{{{RESEND_UNSUBSCRIBE_URL}}}`, stops return by webhook); otherwise one outbox mail per subscriber in their language with the Forum's own stop link, up to 100 sent at once and the rest by the cron's outbox step (Resend's free plan allows 100 transactional mails a day; the desk says so). Never send to pending or unsubscribed rows, never put HTML from a user into a mail.
- Progressive web app: `site/manifest.webmanifest`, `site/sw.js` (bump `CACHE` when the shell changes; never caches `/api/`), registered only on https. `site/embed.js` is the card other sites paste; `/api/dashboard` answers it with CORS, counts only.
- Home page speed (owner's ask, 8 Oct 2026; PageSpeed mobile went from 77 with a 4.1 s largest paint to 100 with 1.9 s in local Lighthouse runs): `site/boot.js` is the only render-blocking script and must stay tiny. It applies the saved theme, sets `html[data-boot=home]` on the English home URL so `styles.css` shows `#v-home` before `data.js` and `app.js` (both `defer`) arrive, and injects the Google Fonts stylesheet so it never blocks the paint (a `<noscript>` copy stays in `index.html`). `route()` removes the flag on its first run. Hindi visitors and every other view wait for `app.js` as before, so no wrong language or wrong page ever flashes. `.tiles:empty` reserves the tile grid's final height per breakpoint (17 tiles of 92 px), so nothing jumps when the tiles render; change those numbers if the issue count or tile size changes.

# Deploying the Forum: Vercel + Supabase

Decided 7 October 2026: the site runs on Vercel (static files plus API functions) and Supabase (Postgres, Storage, Auth). This replaces the Cloudflare + Freshdesk plan in the launch guide; the phases there still apply, with Phase 2 and 3 done by this repository instead of a vendor and a freelancer. Domain: gurugramvisionforum.org, with gurgaonvisionforum.org redirecting to it.

## What runs where

| Piece | Where | Notes |
| --- | --- | --- |
| Website | Vercel, static from `site/` | No build step. `vercel.json` sets `outputDirectory` to `site`. |
| `/api/*` (report, report/upload-url, report/attach, status, join, dashboard, ward, geocode, follow, public/report, public/reports, cron/daily, hooks/whatsapp, hooks/exotel, triage/*) | One Vercel serverless function, `api/index.js`, reached through the `/api/:path*` rewrite in `vercel.json` and routing to `lib/handlers/` | Node 20+, ESM. Holds the Supabase service key. One function because the Hobby plan caps deployments at 12; a 13th file under `api/` fails the deploy with `exceeded_serverless_functions_per_deployment`. |
| Reports, events, joins, master data | Supabase Postgres, schema in `supabase/migrations/` | Row Level Security on every table. Anon key reads master data only. |
| Photos and documents | Supabase Storage bucket `report-photos` | Private, 10 MB per file, images and PDF, at most 8 files per report. The browser never holds a storage key: `/api/report` returns a one-hour upload token, `/api/report/upload-url` turns it into signed upload URLs, `/api/report/attach` records the files on the report. The desk reads them through short-lived signed URLs. |
| Volunteer logins | Supabase Auth + `staff` table | Rows in `staff` grant access to reporter details. |
| Volunteer desk | `#/desk` in the main site + `api/triage/*` | List, filter and update reports; manage accounts. Bearer token from Supabase Auth on every call; the API uses the service role after checking `staff`. |

   - Every report stores the resident's ward, the detected ward and its source; the desk flags a mismatch so volunteers can correct it.

## Daily cron, email and inbound channels

- `vercel.json` schedules two cron calls (the SEO group is a third, run from GitHub Actions `seo-cron.yml` at 21:30 UTC, see below), both with `Authorization: Bearer $CRON_SECRET`: `GET /api/cron/fetch` at 18:30 UTC (00:00 IST: news sources and link checks, the slow network steps) and `GET /api/cron/analyse` at 02:30 UTC (08:00 IST: pulse, round-up, digest, SLA digest, the daily brief to owners and coordinators, outbox, retention) (signals, insights, weekly round-up, digest, IndexNow, SLA digest, outbox, retention). A Vercel function gets 60 seconds, so the two groups never share one invocation. `GET /api/cron/daily` runs everything (or `?steps=news,links`) for manual use; the GitHub Actions workflow "Run the daily cron now" calls both groups on demand (repository secret `CRON_SECRET`, or the run input). Vercel sends `Authorization: Bearer $CRON_SECRET`; set `CRON_SECRET` in the project (any long random string). The run does three things and reports each: the SLA digest (reports unmapped past 3 working days or filed past 21 days, emailed to `COORDINATOR_EMAIL` with references and desk links only), the outbox (stage-change emails to reporters who gave an email and to followers, sent through Resend when `RESEND_API_KEY` and `MAIL_FROM` are set; without a key the rows wait in `outbox`), and the retention sweep (reports resolved more than 24 months ago are deleted with their attachments).
- **Team, inbox, performance, daily brief.** Desk → Roles: one roster (name, mobile, email, desk role, active) where each person is given wards as coordinator (a cluster of 5-6), main lead or support lead; the ward matrix below is derived from it. Desk → Inbox: mail that reaches `/api/hooks/email` (Resend inbound webhook with `RESEND_WEBHOOK_SECRET` + `RESEND_API_KEY`, or any forwarder with `EMAIL_HOOK_TOKEN`), new join requests and unmapped reports in one stream. Desk → Performance: ageing per ward and activity per person. Every morning at 08:00 IST the cron emails the brief to active owners and coordinators (needs the Resend key) and sends owners the one-line version on WhatsApp through the approved template `gvf_daily_brief` (needs the Meta values and a template with one body parameter; create it in WhatsApp Manager as a utility template, English, body `{{1}}`).
- **Social publishing.** Desk → Content → Settings → Social publishing shows which accounts are connected. Connect one by adding its keys in Vercel (all of `META_PAGE_ID` + `META_PAGE_TOKEN` for the Facebook Page, plus `META_IG_USER_ID` for Instagram; `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID`; `BLUESKY_HANDLE` + `BLUESKY_APP_PASSWORD`; the four `X_*` keys) and redeploying; the step-by-step for each account is in docs/social-publishing-research.md. A post ticked "Also share to" goes out when it is saved as published; a published post's Share button does the same later; the cron's `social` step retries anything queued. Every attempt is a row in `social_posts` with the link to the live post or the error.
- **Upkeep.** The API runs in Vercel's Mumbai region (`bom1`), so the midnight link check reaches India-only government hosts. Every official link is checked every night; the footer's "Links verified" date comes from that run through `/api/dashboard` (`links`). An outside monitor (UptimeRobot, free plan, email alerts) watches the live site and replaces the 30-minute GitHub Actions probe `uptime.yml`, removed on 10 Oct 2026; the nightly QA run calls `scripts/check-health.mjs` against production and opens "Nightly checks failed" on a down database, a stale cron, broken links or failed mail. Add a free external monitor (UptimeRobot or Better Stack) with SMS for minute-level alerts.
- **Asking the reporter from the ticket.** On a ticket whose filing checklist is incomplete, "Ask the reporter for the missing items" mails the reporter from `MAIL_FROM` at once (bilingual, the reference in the subject as `[GVF-…]`, Reply-To `DESK_EMAIL`, by default `desk@gurugramvisionforum.org`) and logs it on the timeline; without an email on the report the desk copies the same text for WhatsApp or SMS. The reply reaches `/api/hooks/email` (Resend receiving), is linked to the report by its reference, its photos are stored on the report and the reply appears on the ticket with "Fill the missing fields from this reply", which asks the AI chain (`GROQ_API_KEY`; without a key the fields are filled by hand) for a proposal that a volunteer applies with one click. Needs the receiving MX on the root domain (already set) and the `email.received` webhook; any address at the domain is delivered.
- Stage changes are queued by a database trigger (`reports_notify_stage`), so every path that moves a report (desk, API, SQL) notifies the same way. Bodies carry the reference, stage, desk and ticket and a tracking link; never a name or number.
- Reports are confidential: there is no public report page, map or feed (removed 8 Oct 2026 on the owner's decision). The public sees counts only: `/api/dashboard` (always, no threshold), `/ward/:n` and the Wards page (per ward: total, by stage, by issue, through the `ward_counts()` function). `/r/<ref>` and `/map` show a "Reports are private" notice for old links. The site shows them at `/r/<ref>` and `/map`, with follow-by-email (`POST /api/follow`; one-click unsubscribe link in every mail).
- WhatsApp: point the Meta Cloud API webhook at `https://gurugramvisionforum.org/api/hooks/whatsapp` (subscribe to `messages`) with `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_APP_SECRET`, `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_ID` set. Texts become reports with `source = whatsapp` (issue type "Something else" until the desk maps them) and the sender gets the reference back; a message quoting a reference gets its stage. Exotel: set the passthru or status-callback URL to `https://gurugramvisionforum.org/api/hooks/exotel?token=<EXOTEL_WEBHOOK_TOKEN>`; calls become reports with `source = phone` and the recording link in the description. Both dedupe on the provider message or call id (`inbound_messages`).
- Real URLs: `/report`, `/track/<ref>`, `/privacy` and the other views are rewritten to `index.html` and moved into the hash by the app, so links shared from the site work and unfurl (OG tags and `og.png`).
- Volunteers change their own password from the desk header (`POST /api/triage/password`, 10+ characters with letters and a number).

## Visitors, content, news and checks

- **Visitor registration.** `GVF.GATE` (`site/data.js`) shows a registration form after 90 seconds or on the second page view (never on the desk). In soft mode (default) it asks name and mobile, with email, sector and PIN code optional, and offers "Not now" (asks again after a week); `mode: "hard"` in `GVF.GATE` removes "Not now" and requires the form. Either way there is a consent notice; registrations land in `visitors`, and the site logs first-party events (`visitor_events`) without any third-party tracker. The desk Visitors tab (managers) shows counts and the list and exports a CSV. Read `docs/visitor-data-research.md` before changing the notice: the Forum is a Data Fiduciary under the DPDP Act 2023; the notice must stay itemised, bilingual and withdrawable, which is why the default is the soft mode with the fewest required fields.
- **Content dashboard.** Desk → Content (owner, coordinator): stories, news, photos, videos (upload to the public `media` bucket, 20 MB), social posts (link to the post on X, Facebook, Instagram, YouTube; no embed scripts), testimonials and pop-ups with a time window; publish/unpublish/pin; social account links for the footer. Published items appear within two minutes (`/api/content` is cached 120 s). "Draft with AI" writes English and Hindi drafts for the team to edit; nothing publishes without a person. It runs on a free API: create a key at console.groq.com (no card) and set `GROQ_API_KEY` in Vercel; Claude (`ANTHROPIC_API_KEY`, paid) is only a last resort when Groq fails. Gemini is no longer used (owner's decision, 10 Oct 2026). Free tiers cap requests per minute and per day, which is plenty for a team drafting a few posts a day.
- **Official news.** The daily cron fetches `data/news-sources.json` (RSS or simple HTML pages of the official bodies) into `news_items`; `/news` shows them grouped by day with the source. `.github/workflows/news-sources.yml` probes every source weekly from GitHub Actions (the sandbox cannot reach *.gov.in); `docs/news-sources-notes.md` records the latest result and which sources are on, off and why. When the JSON changes, write the live `news_sources` rows too (insert … on conflict do update; the cron only seeds an empty table).
- **Roles.** Four staff roles, enforced by the API and mirrored by the desk tabs: `owner` (everything, including visitor data and account removal), `coordinator` (reports of all wards, map, team, content, pulse, health), `triage` (ward volunteer: reports and map of the allotted wards only), `content` (content team: Content and Pulse only). The coordinator creates volunteers and content accounts; only the owner creates coordinators. Changing a role is an edit of `staff.role`.
- **Auto-translation.** On the Content form, typing a title, summary or body in one language fills the other when it is empty (English → Hindi or Hindi → English), and the Translate button redoes it on demand. Same keys as drafting (`GROQ_API_KEY`); without a key the form says so and the team writes both by hand.
- **Gurugram pulse.** The daily cron reads public discussion about civic problems in Gurugram (Reddit's public JSON for r/gurgaon and r/gurugram and Google News RSS searches; the reports residents send the Forum are confidential and are never fed into the pulse), classifies each item into the site's issue types and areas (`signals`, kept 60 days, no author names or handles stored), and writes the week's insight (`insights`): top topics with counts by source, areas, example links, trend against the previous week, a headline and summary in both languages and suggested actions (cleaning drive, drain walk, sterilisation camp, townhall…). `/pulse` shows it to everyone; the desk Pulse tab (owner, coordinator, content) adds the raw signals. X/Twitter (no free API) and Quora (scraping forbidden) are not read. With a free AI key the narrative is written by the model; without one it is rule-based.
- **Search visibility.** Server-rendered pages for search engines and sharing: `/guides` and `/guide/<issue>` (17), `/ward/<n>` (36), `/blog` and `/blog/<slug>`, each also under `/hi/`, with canonical, hreflang, Open Graph and JSON-LD (HowTo and FAQ on guides, BlogPosting on posts). `/sitemap.xml` lists them all; `robots.txt` points to it. Set `SITE_URL=https://gurugramvisionforum.org` once the domain is live (until then the Vercel production URL is used). Google: add the domain in Search Console (Domain property, DNS TXT record on the domain in Vercel) and submit `/sitemap.xml`; Google accepts no other ping for ordinary pages. Bing, Yandex and the others: the cron pings IndexNow with the pages published that day (`INDEXNOW_KEY` set; key served at `/indexnow-key.txt`; switch in the desk under Content → Weekly round-up and search engines).
- **SEO desk.** Desk → SEO (owner, coordinator, content team) shows what the machine does for search every night and what it found: the activity log (audit, PageSpeed, news search, IndexNow ping, round-up, link check), the consultant's checklist of 17 items (automatic ones proved by the audit rows; tick "Search Console verified" and "Bing Webmaster Tools verified" once done, the only manual steps), the page audit of every sitemap URL (worst first, with the issue and the fix), Core Web Vitals per key page, "Write next" (topics the city discusses that the site has not covered, with a Draft this button) and the Forum's mentions in the news. The page audit and the mentions search run in the midnight `fetch` cron, so the tab fills on its own; Core Web Vitals come from GitHub Actions `seo-cron.yml` at 03:00 IST (all three steps, one call each because PageSpeed can take most of the function's minute), which needs the repository secret `CRON_SECRET` (GitHub → Settings → Secrets and variables → Actions → New repository secret, the same value as in Vercel; the "Run the daily cron now" workflow needs it too). Run the workflow by hand after adding the secret to see the first PageSpeed row. `PAGESPEED_API_KEY` is needed in practice: without it Google answers 429, because every keyless caller shares one anonymous daily quota, and the SEO tab says so. It is free (25,000 calls a day): Google Cloud console → APIs & Services → Library → enable "PageSpeed Insights API" → Credentials → Create credentials → API key → restrict it to the PageSpeed Insights API → add it in Vercel as `PAGESPEED_API_KEY` (Production) and redeploy. Bing: at bing.com/webmasters sign in and import the site from Search Console, nothing to add on the site.
- **GEO, clusters and search data.** The SEO tab now has six sub-tabs. *GEO*: `/llms.txt` and `/llms-full.txt` are served automatically; robots.txt welcomes the AI crawlers; every page gets a GEO readiness score; with `GROQ_API_KEY` set the nightly run asks Groq (with its web search) three of the questions residents ask and shows whether the answer cited the Forum. *Clusters*: one per issue with the guide as pillar; tag a post with the issue id (roads, waste, water…) to put it in a cluster, and the guide and post link to each other by themselves. *Search data*: Google Search Console needs `GSC_SERVICE_ACCOUNT` (Google Cloud → IAM & Admin → Service accounts → create one, Keys → Add key → JSON; add its email as a Full user in Search Console → Settings → Users and permissions; paste the whole JSON into Vercel) and gives 28-day queries and pages, index status for 10 pages a night and the sitemap status; Bing needs `BING_WEBMASTER_API_KEY` (Bing Webmaster Tools → Settings → API access) and gives queries, pages and crawl stats. All three run in the GitHub workflow `seo-cron.yml` at 03:00 IST; redeploy after adding a key.
- **Vercel's daily deploy limit.** On 8 Oct 2026 the project hit the Hobby plan's limit of 100 deployments in 24 hours (every push to a pull-request branch makes a preview deployment that counts) and a merge to main was silently not deployed; the owner upgraded the plan the same day. If a merge ever fails to appear in Vercel's deployment list again, check the plan's limits and press Redeploy on the latest production deployment. The SEO workflow checks that the live site serves `/llms.txt` before it asks for the GEO and search-data steps, and the cron refuses a request that names only steps it does not know (an older deploy used to run every step instead).
- **Weekly round-up.** Every Monday 03:30 UTC the cron drafts "Gurugram civic week" from the pulse, the week's official notices, the Forum's own counts (once 50 reports exist) and the suggested actions, in English and Hindi (model-written with a free key, templated without), and emails `COORDINATOR_EMAIL`. It sits unpublished for 48 hours (desk: Hold, Release, Publish now; settings: weekday, review hours, 0 = at once, -1 = never) and then publishes itself with the byline "Gurugram Vision Forum data desk" and a disclosure line. Confirmed subscribers (footer form, double opt-in, `subscribers`) get it by email through the outbox.
- **Subscribers and the newsletter tool.** Desk → Subscribers (owner only) lists every sign-up with its state (confirmed, pending = has not clicked the confirmation link, unsubscribed), search, CSV export, Stop emails / Put back / Erase per address and "add an address" (which only sends the confirmation mail). The list is mirrored to Resend contacts, free up to 1,000 contacts with unlimited Broadcasts: in the Resend dashboard the team writes a Broadcast in the editor and sends it to all contacts; Resend adds its own unsubscribe link and the `contact.updated` / `contact.deleted` webhooks bring every stop back to the Forum's own list. Setup: the `RESEND_API_KEY` in Vercel must be a *full access* key (a sending-only key answers 401 and the desk shows "mirror failed: restricted_api_key"); in Resend → Webhooks add `https://gurugramvisionforum.org/api/hooks/email` with the events `email.received`, `contact.created`, `contact.updated`, `contact.deleted` and put its signing secret in `RESEND_WEBHOOK_SECRET` (one endpoint, one secret, for mail and contacts). Older accounts still on Audiences set `RESEND_AUDIENCE_ID`; `AUDIENCE_SYNC=off` pauses the mirror. The nightly `audience` cron step re-pushes anything that failed (rows with `synced_at` null); the Sync button on a row does the same at once. Past 1,000 contacts, export the CSV into Brevo (free, 300 mails a day, unlimited contacts) or Kit (free to 10,000 subscribers) rather than paying Resend's ₹3,400 a month tier.
- **Newsletter, written and sent from the desk.** Desk → Newsletter (owner, coordinator, content team): start blank or from a published post, write the subject and body in English and Hindi (plain text; "## " heading, "- " list, blank line paragraph, links auto-detected; the Translate button fills the other language), Preview, "Send me a test" (lands in the signed-in person's inbox), then "Send to subscribers" (owner and coordinator only; a confirmation names the count). Nobody opens Resend's dashboard. How it goes out is decided by the server: (a) **one Broadcast** when `RESEND_SEGMENT_ID` is set, which is the way to run it: in Resend → Contacts create a segment of all contacts (or use the default audience id on an older account as `RESEND_AUDIENCE_ID`), copy its id into Vercel; the mirrored list receives one mail, Resend adds its stop link and every stop comes back through the contact webhook; no daily cap; (b) **the outbox** without a segment id: one mail per subscriber in their language with the Forum's own stop link; up to 100 go out at once and the rest with the 08:00 IST cron run, because Resend's free plan allows 100 transactional mails a day. The desk's note at the top of the tab says which applies and how many confirmed subscribers there are. The list below the form keeps every draft and sent newsletter with its counts.
- **Installable app and sharing.** The site is a Progressive Web App (install nudge after a report; works offline for the shell). WhatsApp, copy-link and native share buttons sit on reports, posts and the pulse. RWAs and local sites can paste `<script src="https://gurugramvisionforum.org/embed.js" data-ward="15" async></script>` for a "Report it" card.
- **Automated checks.** Cron: 15 official links a run → `link_status`, `cron_runs`. `/api/health` and the desk Health tab: database, storage, last cron run, email queue, broken links, stale news sources. GitHub Actions: unit + smoke on every push and pull request; nightly `scripts/check-links.mjs` over every link in `site/data.js`, opening a GitHub issue "Nightly checks failed" when one breaks.

## Checks after each deploy

- `GET /api/dashboard` returns counts by issue, ward and stage from the first report (`published` is always true).
- Submit a report from a phone: the confirmation shows a server reference (the device shows "saved on this device only" if the API is unreachable).
- Track page: reference plus last four digits of the mobile returns the stage; a wrong last four is refused.
- Report form, step 3: choosing an issue shows "Needed to file with <portal>" with the portal's fields and document slots (`GVF.FILING` in `site/data.js`, mirrored in `issue_types.filing`). After submitting, the confirmation lists anything still missing and the upload status.
- Desk, report detail: the filing checklist shows each portal field and document as present or Missing, with the files as links, and offers "Ask the reporter for the missing items" (copies a message; opens email when the reporter gave one).
- Language toggle: every public page, panel, sheet, form and confirmation switches fully between English and Hindi (the desk stays English). The smoke test checks each route in Hindi for leftover English words.
- `/r/<ref>` and `/map` show the "Reports are private" notice; `/api/public/reports`, `/api/public/report` and `/api/follow` answer 404; `/ward/15` shows counts and no reference.
- `node tests/smoke.mjs` passes locally; `npm test` runs the unit tests for the API validation.

## Privacy, as enforced

- Phone numbers and names live in `reports` and `joins`, readable only by `staff` or the service role.
- The status endpoint returns stage, dates, desk and official ticket number. Nothing about the reporter.
- The dashboard endpoint returns counts and medians only. Every response from the site carries HSTS and a Content-Security-Policy (check with `curl -I https://gurugramvisionforum.org/`).
- IP addresses are stored as salted hashes for rate limiting (5 reports per address per hour).
- Filing details (`reports.extra`, for example a DHBVN account number or a Property ID) and attachments are reporter data: readable only by `staff` or the service role, never returned by the status or dashboard endpoints.
- Retention: reports are to be deleted 24 months after closure. A scheduled job for this is a next build item.
